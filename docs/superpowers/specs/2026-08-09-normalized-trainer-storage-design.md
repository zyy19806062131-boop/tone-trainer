## 1. 背景与已确认事实

线上 `trainer_data` 目前把所有项目、句子和内嵌音频放在 `app_state` 的一个 JSONB 行里。当前线上行仍是 2026-06-21 的旧数据：17 个项目、184 条音频；旧 HSK1 是 195 句，新 HSK1 不存在。

本地成品没有丢失：

- 旧 HSK1（`hsk1`）：15 课、153 句，153 句都有女声原速和慢速音频。
- 新 HSK1（`nhsk1`）：15 课、198 句，198 句都有女声原速和慢速音频。
- 合并两版后的目标状态：18 个项目、415 条音频；原线上其余 16 个项目保持不变。

三套候选整包为 78,145,965 bytes，两版 HSK1 候选整包为 35,948,981 bytes。两次只回滚演练均在当前 256MB Postgres 中触发后端进程被 signal 9 杀死；把 351 条音频拆成 18 批导入临时表后，临时 JSONB 在逐批长到目标体积时仍触发相同结果。所有演练均未执行正式更新或提交，演练后线上 MD5、更新时间和项目/音频计数保持不变。

因此根因是单行大型 JSONB 的存储与重写方式超过当前数据库内存上限，不是本地成品缺失，也不是单个导入命令故障。

## 2. 目标

1. 不升级 Render 数据库套餐，不增加月费。
2. 恢复旧 HSK1 153 句与新 HSK1 198 句及各自两档语速音频。
3. 线上其余 16 个项目、访问码和权限规则不变。
4. 不再创建或重写包含全部音频的单个 JSONB 行。
5. 代码部署、数据装入和启用彼此分离；任一步失败时继续使用当前旧数据。
6. 保留一条快速、可验证的回退路径。

## 3. 本轮不做

- 不修改前台布局、交互、访问码或管理员操作方式。
- 不重新生成、替换或人工修订现有音频。
- 不在本轮上线新 HSK2（`nhsk2`）。规范化存储消除数据库单行限制，但新 HSK2 上线前仍需单独检查登录响应体积和网页内存。
- 不删除或覆盖旧 `app_state.trainer_data` 行。
- 不把私有训练数据、访问码、数据库连接串或备份提交到 Git。

## 4. 数据结构

服务启动时创建三张表；创建空表不会启用新存储。

### `trainer_store_meta`

一条很小的启用记录，同时保存顶层元数据和期望计数。

| 字段 | 约束 | 用途 |
|---|---|---|
| `id` | `SMALLINT PRIMARY KEY`, 固定为 `1` | 单例启用开关 |
| `payload` | `JSONB NOT NULL` | 保存 `_dataVersion` 等顶层字段，不含 `decks`/`audio` |
| `expected_deck_count` | `INTEGER NOT NULL` | 完整性检查 |
| `expected_audio_count` | `INTEGER NOT NULL` | 完整性检查 |
| `updated_at` | `TIMESTAMPTZ NOT NULL` | 最近启用时间 |

### `trainer_decks`

每个项目一行。

| 字段 | 约束 | 用途 |
|---|---|---|
| `deck_id` | `TEXT PRIMARY KEY` | 项目 ID |
| `deck_order` | `INTEGER UNIQUE NOT NULL` | 保持原项目顺序 |
| `payload` | `JSONB NOT NULL` | 该项目的 `name`、`units`、`sents` 等完整内容 |
| `updated_at` | `TIMESTAMPTZ NOT NULL` | 最近写入时间 |

### `trainer_audio`

每个句子音频一行，单行只含一个句子的声音版本。

| 字段 | 约束 | 用途 |
|---|---|---|
| `sentence_id` | `TEXT PRIMARY KEY` | 句子 ID |
| `deck_id` | `TEXT NULL`、普通索引 | 所属项目；历史孤立音频允许为空并原样保留 |
| `payload` | `JSONB NOT NULL` | 该句的女声/男声/儿童声及原速/慢速数据 |
| `updated_at` | `TIMESTAMPTZ NOT NULL` | 最近写入时间 |

不对 `trainer_audio.deck_id` 建外键。当前目标数据中有 16 条历史音频找不到现存句子；它们虽不会发给学生，但必须作为“线上其余数据不动”的一部分保留。

## 5. 读取、写入与启用

### 读取

`load_json(DATA_PATH)` 保持原有返回格式，但内部增加规范化读取：

1. `trainer_store_meta` 没有 `id=1`：读取旧 `app_state.trainer_data`，行为与当前线上完全相同。
2. 启用记录存在：按 `deck_order` 读取 `trainer_decks`，读取 `trainer_audio`，重建原有 `{_dataVersion, decks, audio}` 结构。
3. 实际项目数或音频数与启用记录不符：记录明确警告并退回旧 `app_state.trainer_data`，不把半套数据交给学生。

现有 `build_payload()`、访问码过滤、管理员页面和前端收到的数据结构不变。

### 写入

数据库模式下，`save_json(DATA_PATH, payload)` 改为一个事务内：

1. 校验顶层结构、项目 ID/顺序和音频字典。
2. 写入或替换项目行和音频行，并删除逻辑数据中已经不存在的旧行。
3. 最后更新 `trainer_store_meta` 的顶层元数据及期望计数。
4. 任一步异常时回滚整个事务，读者继续看到上一次完整状态。

访问码仍使用原来的小型 `app_state.access_codes` 行，不参与本次迁移。

### 首次启用

1. 先部署兼容代码。新表为空，因此线上仍读取旧 `app_state.trainer_data`。
2. 部署后先验证首页、登录和旧项目仍可用。
3. 导入脚本从写前线上备份出发，只用本地 `hsk1`/`nhsk1` 替换或新增目标项目；其余 16 个项目逐项保持相等。
4. 在一个数据库事务中按小行写入 18 个项目、415 条音频和顶层元数据。
5. 在同一事务内核对项目总数、音频总数、目标句数、目标音频内容及线上备份并发保护；全部通过后才写入启用记录并提交。
6. 提交前，任何线上请求仍看到旧数据；提交后，新请求才看到完整的新数据。

## 6. 并发、安全与回退

- 导入前再次核对旧 `trainer_data` 行的 MD5 与写前备份一致；不一致就停止，由人工重新合并，不覆盖别人的新修改。
- 导入和管理员保存使用同一把 PostgreSQL 事务级 advisory lock，防止两个写入同时切换；锁在提交或回滚时自动释放。
- 私有 JSON、CSV、SQL、音频、访问码和连接串继续放在 Git 忽略目录或本机私密位置。
- 快速回退在一个专用事务中仅执行 `DELETE FROM trainer_store_meta WHERE id = 1` 并提交该受限变更；项目/音频小行保留作核查。提交后必须回读确认 `meta=0`，并确认应用服务的是未改动的旧 `app_state.trainer_data`。
- 代码回退同样安全：旧版本服务器不知道新表，会继续读取旧 `app_state` 行。
- 确认稳定前不删除旧行；本轮也不设计删除日期。

## 7. 测试设计

实施采用测试先行，至少覆盖：

1. **拆分/重建等价**：把含历史孤立音频和无音频句子的逻辑数据拆成行后重建，结果与原对象完全相等。
2. **未启用回退**：新表为空或无启用记录时，仍返回旧 `app_state` 数据。
3. **正常启用**：启用记录和计数一致时，返回按正确顺序重建的新数据。
4. **不完整保护**：项目或音频行缺失时，记录警告并返回旧数据。
5. **事务回滚**：在项目、音频和启用记录三个阶段分别注入失败，均不暴露半套状态。
6. **权限回归**：原有访问码的项目/单元过滤和音频过滤结果不变。
7. **合并回归**：目标必须是 18 个项目、415 条音频；`hsk1=153`、`nhsk1=198`，351 个目标句子都有 `f.n`/`f.s` 两档内嵌 MP3。
8. **无关数据保护**：原线上其余 16 个项目逐项相等，非目标音频逐项相等。

## 9. 后续边界

本设计解决数据库单行 JSONB 的硬上限，并为后续项目提供小行写入基础；它不自动证明 42MB 的新 HSK2 适合继续随登录响应一次性发给浏览器。两版 HSK1 稳定后，新 HSK2 需先做真实登录响应体积、服务内存和浏览器播放测试，再决定直接启用或增加按需音频接口。
